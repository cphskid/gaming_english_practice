> 狀態：**架構已拍板，細節可調**。可讀版本：https://claude.ai/artifact/JsECWLS77m7wD7yD9W5FXw

> 日期：2026-09-19

---

## 0. 一句話

**答題事件是唯一的真相來源**，其他東西（金幣、經驗、星星、排行榜、老師報表）全都是從事件算出來的結果，不是各自獨立存的資料。

這是整份文件裡唯一「之後改會很痛」的決定，其餘都可以邊做邊調。

---

## 1. 依賴方向

```
        ui  ──→  games  ──→  core  ──→  data
                              ↑
                             net   （被注入，不是被 import）
```

規則只有一條：**箭頭不可以反向**。

- `core` 不知道 `games` 存在 → 新增一個遊戲不用改養成系統
- `games` 不知道 `ui` 存在 → 換介面皮不會動到遊戲邏輯
- `core` 不知道 Supabase 存在 → 換資料庫只改 `net`
- `data` 誰都不知道 → 純資料，可以被老師後台、報表、遊戲共用

守住這一條，就不會「骨架歪了要重刻」。歪掉通常不是因為選錯框架，是因為某個模組偷偷去讀了不該讀的東西。

## 2. 模組

### `data/` — 純資料，零邏輯

| 檔案 | 內容 |
|---|---|
| `words/core300.json` | 300 字題庫（已完成），**用 id 當鍵，不要用單字字串** |
| `levels/*.json` | 14 關：主題、地圖、路徑、塔位、波次、魔王 |
| `towers.json` / `enemies.json` | 塔與怪的數值 |
| `shop.json` | 商品、價格、解鎖等級 |
| `achievements.json` | 成就條件 |

關卡是資料不是程式，所以之後 Chuck 自己就能改難度，不用等我。

### `core/` — 規則與狀態，不碰 DOM、不碰網路

| 模組 | 負責 | 為什麼獨立 |
|---|---|---|
| `quiz` | 出題、判定對錯、選字策略（複習常錯的字） | 三個遊戲共用同一套出題邏輯 |
| `wordStat` | 每個字對這個學生的答對／答錯／反應時間，**分能力維度** | 老師報表和針對性複習都靠它，是最有價值的資料 |
| `economy` | 金幣計算，含「同字重複答對遞減」 | 錢只有一個出口，才不會某個遊戲給太大方 |
| `progress` | 經驗、等級、關卡星星與解鎖 | |
| `inventory` | 道具與裝飾品背包 | 跨遊戲共用，打地鼠賺的道具要能帶進守塔 |
| `character` | 角色存檔、職業、外觀 | 與帳號分開（見第 6 節） |
| `session` | **一場遊戲**：關卡 × 模式 × 參與者 × 事件收集 | 模式規則住這裡，不住遊戲裡 |

### `games/` — 每個遊戲一個資料夾

守塔、打地鼠，之後還會有別的。**遊戲只做三件事**：吃一份關卡資料、跑自己的玩法、回報答題事件。

**遊戲不算金幣、不算經驗、不算星星。** 這是硬性界線。詳見第 3 節。

### `net/` — 唯一知道資料存在哪裡的地方

一個介面，兩個實作：

```
Repository {
  loadCharacter(studentId)
  saveEvents(events[])
  loadProgress(studentId)
  joinRoom(code, nickname)
  subscribeRoom(roomId, onUpdate)
}
```

`net/local` 存 localStorage，`net/supabase` 存雲端。`core` 只認介面，換一行注入就切換。

### `audio/` — 音訊模組

統一處理 iOS 解鎖、音量、靜音開關、缺檔時用 Web Audio 合成佔位音。已備妥的檔案見 `assets/audio/README.md`。

### `ui/` — React 元件

登入、選關地圖、遊戲容器、結算、商店、角色、老師後台。

## 3. 多個遊戲怎麼搭

這是整份架構裡最容易做歪的地方：每加一個遊戲都要改一次 core，或是某個遊戲變成刷錢機。

### 每個遊戲的定位不一樣

| 遊戲 | 定位 | 有關卡 | 主要產出 | 練什麼能力 |
|---|---|---|---|---|
| **單字守塔** | 主線 | 有，14 關 | 星星、經驗、進度 | 看中文認英文 |
| **打地鼠** | 快速練習／賺錢管道 | 無，只有回合 | 金幣、道具 | 認字速度 |
| 拼字（未來） | 拼寫關 | 有，綁 180 個拼寫字 | 經驗、道具 | 拼得出來 |
| 聽力（未來） | 練習管道 | 無 | 金幣 | 聽音辨字 |

### 答題事件要帶「能力維度」

**「會這個字」不是一件事，是三件事：認得出、拼得出、聽得懂。**

所以答題事件要帶一個 `skill` 欄位（`recognize` / `spell` / `listen`），`wordStat` 也要分維度記。否則小朋友在打地鼠把 `apple` 點對十次，系統會以為他學會了而不再複習，但他其實一個字母都拼不出來。

**這個欄位現在加成本是零；等拼字遊戲做出來才加，代表之前所有答題紀錄都要重來。**

### 所有遊戲共用同一份契約

遊戲不 import core，是 core 把該給的東西包成 `ctx` 遞給遊戲（依賴反轉），所以每個遊戲都能單獨測試。

```ts
interface GameModule {
  id: string              // 'tower-defense'
  name: string            // '單字守塔'
  skill: Skill            // 這個遊戲練哪個能力
  hasLevels: boolean
  supportedModes: Mode[]  // 支援個人／競爭／團隊哪幾種
  mount(el: HTMLElement, ctx: GameContext): GameHandle
}

interface GameContext {   // core 給遊戲的東西，遊戲只看得到這些
  level: LevelData | null
  quiz: { next(): Question }
  report(r: AnswerReport): void   // 唯一的回報管道
  audio: AudioBus
  onEnd(result: GameResult): void
}
```

### 共用什麼、不共用什麼

| 東西 | 共用？ | 為什麼 |
|---|---|---|
| 題庫、出題邏輯 | 共用 | 同一份 300 字，複習策略才會一致 |
| wordStat | 共用 | 在哪個遊戲答錯都算數，老師報表才完整 |
| 金幣、經驗、等級 | 共用 | 只有一條養成線 |
| 道具與裝飾品背包 | 共用 | 「其他遊戲當賺錢管道」就是這個意思 |
| 音效、UI 元件、登入 | 共用 | — |
| 關卡資料 | 不共用 | 只有守塔類的遊戲有關卡 |
| 玩法、畫面、操作 | 不共用 | 本來就該不一樣 |
| 金幣怎麼算 | **遊戲不准碰** | 見下 |

### 防止某個遊戲變成刷錢機

規則只有一句：**一題值多少錢，由字的難度和你答過幾次決定，跟你在玩哪個遊戲無關。**

遊戲唯一能影響的是「一分鐘能答幾題」。所以打地鼠節奏快、賺得多，是因為答的題目多，不是因為它給得大方。這條守住，之後加十個遊戲，經濟都不會崩。

### 加一個新遊戲要做的事

1. 在 `data/` 放它需要的資料（如果有關卡）
2. 在 `games/<id>/` 實作 `GameModule`
3. 在遊戲清單裡註冊一行

不用碰 core、不用碰經濟、不用碰資料庫，**也不用改老師後台**——報表自動涵蓋新遊戲，因為事件形狀一樣。

## 4. 一輪遊戲怎麼跑

```
學生輸入班級代碼＋暱稱
  → net.joinRoom() 取回 character 與 progress
  → 選關，建立 session(level, mode, participants)
  → 遊戲啟動，只跟 core 講兩句話：
        quiz.next()                    「下一題是什麼」
        session.report(wordId, ok, ms) 「答對了，花了 2.3 秒」
  → session 累積事件；competitive 模式同時把事件廣播給房間
  → 遊戲結束
  → core 從事件算出：星星、金幣、經驗、wordStat 更新
  → net.saveEvents() 寫回
  → UI 顯示結算
```

注意遊戲全程沒有碰到金幣、經驗、資料庫。這就是「新增遊戲很便宜」的原因。

## 5. 三種模式怎麼共用關卡

**界線：關卡描述地圖和怪，模式描述規則。**

| | 個人 | 競爭 | 團隊 |
|---|---|---|---|
| 參與者 | 1 人 | 同房多人 | 同房分隊 |
| 比較對象 | 自己的紀錄 | 即時排行榜 | 隊伍總分 |
| 結束條件 | 城堡陣亡或清完波次 | 同上，加上名次 | 同上，加上隊伍勝負 |
| 金幣經驗 | 照常 | 照常 | 照常 |

14 關 × 3 模式 = 42 種玩法，但只要寫 14 份關卡資料 + 3 份模式規則。

**關鍵：`session` 從第一天就設計成多人也成立**，個人模式只是 participants 長度為 1。這樣之後加房間不用回頭改 session，這是「現在不接後端也不會白工」的技術前提。

排行榜是「把事件加總起來」，本地模式加總本地事件，連線模式加總廣播來的事件，**同一份程式**。

## 6. 帳號與角色分開

- **帳號**＝你是誰。學生是「班級代碼＋暱稱」，**不收真實姓名、不收 email**。老師才有真正的帳號（email 登入）。
- **角色**＝你的存檔。等級、金幣、職業、裝飾品。

分開的理由：學生換班、重新加入房間、或之後想要第二個角色，帳號都不用動。合在一起之後要拆很痛。

權限目前只有兩種：學生、老師。

## 7. 資料庫：現在要準備嗎？

**建議：現在不接 Supabase，但現在就把事件的資料形狀定死，而且本地版要照同樣的形狀存。**

理由：

- 會逼我們重刻的不是「後來才加資料庫」，是「資料形狀一開始就錯」。形狀現在定，接線之後做。
- 現在還沒有帳號、沒有房間，先蓋 auth 和 schema 只會一直改。
- 有了第 5 節那個「session 天生多人」的設計，之後接後端不會動到 core。

**什麼時候非接不可**：

1. **競爭／團隊模式一定要後端**，那是即時同步，本地做不了。
2. **第一次讓一整班真的玩之前**必須接好，不然資料只存在各自的平板上，老師報表等於沒有。

所以順序是：骨架 ＋ 個人模式（localStorage）→ 接 Supabase → 房間 ＋ 競爭／團隊模式。

### 之後要建的表（先記著，不急著做）

| 表 | 欄位重點 |
|---|---|
| `teachers` | 綁 Supabase auth，有 email |
| `classes` | 班級代碼、老師 |
| `students` | 班級、暱稱。**沒有姓名、沒有 email** |
| `characters` | 學生、等級、經驗、金幣、職業、裝飾品 |
| **`answers`** | **學生、字 id、能力維度、對錯、毫秒、遊戲、關卡、時間 ← 事件日誌，整個系統的地基** |
| `level_progress` | 學生、關卡、星星、最佳成績 |
| `rooms` / `room_members` | 房間、模式、關卡、成員、隊伍、分數 |

`answers` 的量很小：30 人 × 每場 100 題 × 每週 2 場 ≈ 每週 6,000 列，一年也才三十幾萬列，Supabase 免費額度綽綽有餘。

**存事件而不是只存結果，代表之後 Chuck 想要任何新報表都只是一句查詢，不用改資料結構。**「全班最常錯的字」就是對 `answers` 做一次 group by。

### 防作弊

學生的「班級代碼＋暱稱」不是真的憑證，任何人都能冒充。所以：

- **金幣和經驗不可以由客戶端直接寫入**，要由資料庫函式從答題事件算出來。
- 小朋友真的會找漏洞——第一次試玩就有人發現亂點可以得分。這不是假想敵。

其餘（RLS 讓學生只讀得到自己的存檔和自己在的房間）照 Supabase 預設做法即可，不用過度設計。
